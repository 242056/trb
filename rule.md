Техническое задание: Шаг 0 и Шаг 1

Версия для передачи в работу (разработчик + ИИ-агенты)



Коротко

Зачем. ExplainLaw работает на чужих данных и чужих API. Поставщик уйдёт — продукт встанет. И пока мы на чужой базе, ответы упираются в её потолок: нет нужной полноты и структуры.

Что делаем. Строим свою базу НПА. Она дорогая и долгая, а зарабатывать надо сейчас. Поэтому каждый шаг одновременно приносит пользу сегодня и приближает независимость. Шаг, который делает только одно, — пересматриваем.

Шаг 1. Каждый день забираем свежие федеральные законы с официального портала. Разбираем, что именно изменилось. Раз в неделю публикуем сводку со ссылкой на первоисточник. Параллельно те же данные копятся в базу для следующих шагов.

Откуда данные. publication.pravo.gov.ru — официальный API на чтение. Метаданные и факт публикации берём готовыми. Текст вынимаем из PDF сами. Связи между законами и суть изменений строим сами — этого нет ни у кого, это и есть наш актив.

Кто считает. Дешёвую механику — разбор, сравнение, классификацию — делает локальная модель на своём железе. Публичный текст под брендом пишет облако. Перед публикацией два контроля: сверка фактов с первоисточником и проверка, что сводка не добавила лишнего. Публикуется только то, что прошло проверку, — без человека.

Как храним закон. Не как один текст, а как цепочку изменений. Из неё собираем редакцию на любую дату. Вступление закона в силу ничего не перезаписывает — нужная редакция становится действующей по дате.

Граница. Своя СПС — не цель. Цель — убрать зависимость от чужих данных там, где это критично. Где строить своё невыгодно, оставляем внешние источники.



Как читать документ. Это постановка задачи. Основной приоритет — требования и критерии готовности. Краткие пометки «Почему так» поясняют решения, чтобы исполнитель (человек или ИИ-агент) не переинтерпретировал их по-своему. Требования обязательны к исполнению; пометки «Почему так» — контекст, а не предмет реализации.



Содержание



1. Контекст и цель проекта (Шаг 0)

1.1. Проблема

ExplainLaw зависит от данных и API сторонних поставщиков. Это порождает две разные проблемы:

Риск выживания. Отказ поставщика или изменение условий обрушивает продукт мгновенно, независимо от качества самого продукта.

Потолок качества. Чужие база и API не заточены под задачу: нет нужной полноты, архитектуры и контроля над структурой и связями норм.

1.2. Цель и её граница

Цель — снизить зависимость от чужих данных в критичных местах, где зависимость опаснее всего и где чужие данные хуже всего покрывают задачу.

Граница (важно для объёма работ): создание собственной СПС НЕ является целью. Не закладывать «на вырост» полноту охвата, строгость всех связей, все типы актов и исторические редакции. Действует принцип достаточности — реализуется то, что нужно текущему шагу. Внешние API остаются допустимыми там, где строить своё невыгодно.

1.3. Сквозной критерий приёмки решений

Любое проектное решение проверяется по двойному критерию:

Приближает ли оно независимость от чужих данных в критичных местах.

Даёт ли оно пользователю ощутимую ценность уже сейчас.

Решение, удовлетворяющее только одному пункту, требует пересмотра.

1.4. Метрика успеха

Не «база готова», а растущая от шага к шагу доля критичной функциональности, не зависящей от внешних API, при условии, что каждый шаг уже приносит ценность.



2. Шаг 1 — общее описание и границы

2.1. Что делает Шаг 1

Ежедневный автоматический сбор свежих федеральных законов (ФЗ) из официального источника, их обработка (извлечение текста, дельта изменений, ИИ-сводка) и формирование еженедельного контента для соцсетей. Параллельно — накопление структурированной базы для последующих шагов.

Почему так: шаг двойной по замыслу. Наружу — контент, дающий трафик и доверие (ценность сейчас). Внутрь — накопление актива (независимость в будущем). Требования контента («интересно, читаемо, еженедельно») и базы («полно, структурировано») разводятся архитектурно, чтобы не конфликтовали.

2.2. Границы скоупа (обязательные)



2.3. Реальность объёма (для проектирования нагрузки)

Поток ФЗ: ориентир ~550–800 в год (≈1,5–2 в календарный день в среднем).

Свыше 90% ФЗ — это законы «о внесении изменений». Самостоятельный новый закон без дельты бесполезен для читателя.

Поток крайне неравномерный: к концу сессий — десятки ФЗ за день (подтверждено: 9 апреля 2026 — ~25 ФЗ за день), между сессиями — дни и недели без ФЗ.

Вывод для архитектуры: жёсткий формат «постим в день публикации» нереализуем. Стабильность создаётся буфером и отбором между источником и публикацией (см. раздел 7).



3. Источник данных: publication.pravo.gov.ru

Официальное опубликование — поддомен publication.pravo.gov.ru. У портала есть документированный REST API только на чтение, а также RSS и «Открытые данные». HTML-парсинг для Шага 1 НЕ требуется.

Почему так: официальный машинный доступ сводит зависимость от вендоров на этапе сбора почти к нулю — прямое выполнение критерия из 1.3.

3.1. Фильтр для отбора ФЗ

Блок публикации: president (ФЗ, ФКЗ, указы и распоряжения Президента публикуются здесь, т.к. ФЗ направляет на опубликование Президент).

Вид документа: «Федеральный закон» — отбор по DocumentTypeId.

Блок president содержит вперемешку ФЗ, ФКЗ, указы и распоряжения — фильтрация по виду ОБЯЗАТЕЛЬНА, иначе в ленту попадут указы и распоряжения.

Технический шаг при настройке: точный GUID вида «Федеральный закон» получить запросом /api/DocumentTypes?block=president с сервера и зашить в фильтр DocumentTypeId. Не блокер: альтернатива — фильтрация по полю вида в выдаче /api/Documents.

3.2. Эндпоинты API



Ежедневный рабочий запрос (ориентир): /api/Documents с параметрами Block=president, DocumentTypeId={GUID ФЗ}, PeriodType=daily (или day + Date для конкретной даты). Пагинация: PageSize до 200, Index. Режим API — только чтение.

3.3. Что API отдаёт готовым (поля)



3.4. Чего в API НЕТ (это и есть собственный актив)

Структурированный текст. Текст приходит как PDF/SVG (электронный образ). Полный текст извлекается из PDF самостоятельно (extract; OCR-фоллбэк для сканов).

Связи и дельты. Машиночитаемой ссылки «этот акт изменяет тот» нет — только текст в name. Связь «какой акт изменяется» извлекается самостоятельно.

Даты вступления в силу. В API отсутствуют. Извлекаются из текста PDF и моделируются ПО ЧАСТЯМ (разные статьи вступают в силу в разные даты).

Карта зависимости Шага 1: метаданные и факт публикации — независимы (официальный API); полный текст — независим, но требует своей обработки; дельта, связи, даты вступления, отрасль, группировка — строятся самостоятельно (это и есть фундамент независимости).



4. Модель данных и поля

Принцип хранения: захват сырья и раскладка по полям — разные операции.

Правило: захватываем всё сырьё; заводим все поля; заполняем по достаточности. Пустое поле — бесплатно и обратимо. Потерянное сырьё — невосполнимо. Заводить поля щедро, заполнять скупо, сырьё хранить полностью.

4.1. Категория 1 — Сырьё и происхождение (захватывать всегда)

Полный исходный файл акта (PDF; при наличии — ZIP/SVG), как опубликован.

Ссылка на первоисточник (обязательное поле — основа доверия).

Снимок/копия страницы или файла на момент захвата (источник/ссылка могут измениться).

Дата и время обнаружения акта системой (наше значение, не из акта).

Идентификатор источника и сырые метаданные API «как есть» (без интерпретации).

4.2. Категория 2 — Реквизиты (дёшево, есть сразу)

eoNumber (natural key), number, documentDate.

name, complexName.

publishDateShort / viewDate.

Вид акта (в Шаге 1 всегда ФЗ — поле завести, понадобится далее).

Принявший орган (signatoryAuthorityId).

pagesCount, pdfFileLength, hasSvg, zipFileLength — как поля-подсказки.

4.3. Категория 3 — Производное знание (вычисляется; поле завести сразу)

Краткая ИИ-сводка.

Дельта: что именно меняется.

Какой акт изменяется — хранить как СВЯЗЬ (распознанный идентификатор: номер+дата), отдельно от человекочитаемого названия.

Кого касается / влияние.

Отрасль/категория (нужна в Шаге 4; размечать с самого начала — копит датасет).

Значимость / признак «брали ли в пост» (разметка релевантности на будущее).

Статус полноты дельты: полная (было→стало) / частичная.

Группировка родственных актов.

4.4. Ловушки полей (обязательно учесть)

Дата вступления в силу — не скаляр. Разные статьи одного ФЗ часто вступают в силу в разные даты. Модель: набор дат с привязкой к статьям/частям. Одно поле «дата вступления» приведёт к ошибочным данным.

«Какой акт изменяется» — связь, а не строка. Хранить распознанный идентификатор изменяемого акта отдельно от названия — это будущее ребро базы.

Эффект «пакетов». Идут пачки почти идентичных по теме ФЗ подряд. Нужна механика группировки родственных актов для отбора в пост (иначе один сюжет занимает весь дайджест).

Размер PDF/страниц как сигнал. Разброс от 1 до 140+ страниц. Использовать pagesCount/pdfFileLength для приоритизации и выбора стратегии извлечения.



5. Модель хранения данных (таблицы)

Логическая схема хранения. Имена полей и таблиц — индикативные; типы даны как ориентир (нотация близка к PostgreSQL). Реализация может уточнять имена, но обязана сохранять разделение «сырьё / реквизиты / производное знание» и перечисленные сущности.

Объектное хранилище (с резервированием): бинарные файлы — PDF/ZIP/SVG и снимки страниц. В реляционной БД хранятся только указатели (путь) и контрольные суммы. Это сырьё Категории 1 — невосполнимо, поэтому НЕ только на домашнем диске.

Реляционная БД (PostgreSQL): все структурированные таблицы ниже.

Kafka: транспорт конвейера и развязка между сбором (надёжный контур) и обработкой (домашний сервер).

Связи между актами моделируются adjacency-таблицей npa_relation с типизированными рёбрами; обходы — рекурсивными запросами. Отдельная графовая СУБД на этом этапе НЕ вводится (принцип достаточности). Векторный/семантический поиск — вне скоупа Шага 1.

6. Версионирование норм и задел под атомарную модель

Раздел описывает, как хранится ИЗМЕНЯЕМЫЙ акт (например, статья ГК), который правит ФЗ-поправка. Принцип ниже обязателен. Атомарная (поузловая) модель на Шаге 1 сознательно НЕ реализуется, но архитектура обязана оставлять переход к ней дешёвым.

Источник истины — поток событий-изменений нормы. Текст редакции на любую дату — ПРОИЗВОДНОЕ представление, собираемое из событий. Вступление закона в силу НЕ перезаписывает норму — оно лишь делает соответствующее событие действующим по дате.

6.1. Единица версионирования

Текст версионируется КРУПНОЙ единицей — нормой (статья целиком). Атомарная модель (пункт / часть / абзац) отложена.

При этом гранулярность ИЗМЕНЕНИЯ фиксируется детально в самом событии (адрес единицы, тип операции) — это и есть задел под атомарность (см. 6.4).

Почему так: атомарное хранение текста требует разбора нормы в дерево с подвижной нумерацией и идентичностью узлов ≠ номер (перенумерация при вставке/удалении). Это инженерия уровня СПС — не цель Шага 1. Крупная единица текста + детальное событие даёт почти ту же ценность дешевле.

6.2. Модель: точка отсчёта + цепочка событий

Точка отсчёта — исходный текст нормы на точно зафиксированную дату; оформляется как нулевое СОБЫТИЕ (тип baseline), а не как особый случай. Поток событий однороден.

Каждое последующее изменение — событие со своей датой вступления в силу.

Порядок применения — СОСТАВНОЙ: дата вступления + вторичный критерий внутри одной даты. (Несколько поправок могут вступать в один день — напр. 1 января — и зависеть друг от друга; только дата не задаёт корректный порядок.)

Связь «поправка → изменяемый акт» на уровне акта хранится в npa_relation (5.4); norm_change_event детализирует её до конкретных изменений нормы.

Ловушка: точка отсчёта должна иметь ТОЧНУЮ дату и быть дословно корректной — на ней висит вся цепочка, кривой базовый текст незаметно искажает все вычисленные редакции. Брать выверенную консолидированную редакцию (при необходимости из внешнего источника, приняв временную зависимость).

6.3. Сборка редакции и кэш «текущей»

Редакция на дату X = baseline + все события с датой вступления ≤ X, наложенные по порядку.

«Действующая редакция» НЕ хранится флагом, а ВЫЧИСЛЯЕТСЯ от текущей даты. Вступление закона в силу = не правка нормы, а инвалидация кэша редакции, чья дата наступила.

Кэш собранного текста (norm_revision_cache) — производное, допустимо для скорости; источник истины (события) неизменен.

Вся сборка изолирована за ЕДИНЫМ интерфейсом «дай редакцию нормы N на дату X». Остальной код не знает внутренней механики — это делает переход к атомарности заменой реализации, а не правкой по всему продукту.

6.4. Шесть требований к заделу под атомарную модель

Требование 1 — событие пишется атомарно-детально (даже если текст хранится крупно). Минимальный состав: адрес единицы; тип операции (замена / дополнение / удаление / новая редакция); было/стало (насколько доступно); порядок; ссылка на сырьё.

Требование 2 — адрес единицы структурированный, не строкой. Хранить разобранным на компоненты (jsonb: {статья, часть, пункт, подпункт, абзац}), а не текстом «п.3 ч.2 ст.5».

Требование 3 — стабильный id нормы, отдельный от номера. Идентичность нормы ≠ её номер/название (готовит к будущему правилу «id узла ≠ позиция»).

Требование 4 — точка отсчёта как событие. Однородный поток без отдельной ветки «базовый текст сбоку».

Требование 5 — сборка за единым интерфейсом. Единственное место, знающее механику сборки.

Требование 6 — сырьё сохраняется всегда. Финальная страховка: из сохранённых текстов поправок (Кат. 1) любую модель можно построить заново.

Цена задела — более строгая работа извлечения уже сейчас (Qwen на нормализации вытаскивает адрес и тип операции аккуратно, а не «примерно»). Это та же работа, что нужна для качественной дельты в посте, — окупается дважды.

6.5. Таблицы версионирования

norm — стабильная идентичность нормы (абстрактная статья).



norm_change_event — поток событий (ИСТОЧНИК ИСТИНЫ).

effective_date берётся из расписания вступления в силу поправки (npa_enactment) для соответствующего положения. «Когда узнали» (created_at) ≠ «когда действует» (effective_date) — это битемпоральность.

norm_revision_cache — собранная редакция (ПРОИЗВОДНОЕ, кэш).

Запись кэша инвалидируется/пересобирается при наступлении новой даты вступления для этой нормы. Источник истины (события) не трогается.

6.6. Границы реализации на Шаге 1

Модель цепочки ПРОЕКТИРУЕТСЯ и НАПОЛНЯЕТСЯ (события пишутся детально по 6.4), но полноценная сборка произвольной редакции на Шаге 1 НЕ реализуется.

Поддерживается тривиальная сборка для apply_kind = full_redaction («изложить статью в новой редакции» — новый текст заменяет предыдущий целиком).

apply_kind = address_patch (адресные правки «слова X заменить словами Y») — НЕ собираются автоматически, помечаются apply_status = needs_manual и копятся. Для поста показывается сам патч (см. дельту в 4.3 / 8.3).

Полноценный интерпретатор патчей (наложение операций, перенумерация, реконструкция) и переход к атомарной модели — отложены до потребности консультаций (Шаги 5–7). Благодаря 6.1–6.5 переход = новый интерпретатор за единым интерфейсом + разовая пересборка из накопленных событий, без потери данных.

Ловушка наложения: наложение патча — не «replace в строке», а интерпретатор операций над структурой текста. Обязателен режим «не смог применить» → apply_status = failed/needs_manual, а не молчаливый мусор. Это ещё одна точка контроля качества: несборка останавливает, а не публикует.



7. Конвейер обработки и стабильность контента

7.1. Разделение ритмов

Сбор — ежедневный. Парсер ежедневно опрашивает API и складывает найденное в накопитель (бэклог).

Публикация — еженедельная. Тянет не «что вышло сегодня», а лучшее из накопителя.

Почему так: источник пульсирует (раздел 2.3). Стабильность достигается буфером + редакторским отбором, а не равномерностью источника.

7.2. Накопитель и отбор

Накопитель работает как банк: в пик берём в пост лучшее, остальное остаётся; в засуху достаём из банка.

Пост = N самых значимых изменений (ориентир 3–7), а не весь список за неделю.

Каждое решение «в пост / мимо» сохраняется как разметка релевантности (датасет на будущее).

Запасные форматы против засухи: поток «вступает в силу на этой неделе» (не пересыхает), разборы, мини-дайджесты — 3–4 шаблона поста.

Резерв: всегда держать 1–2 готовых поста. Серийность важнее абсолютной свежести отдельного поста.

7.3. Конвейер обработки одного ФЗ (узел → исполнитель)



Правило фрагментирования (обязательно для узлов 2–3): локальной модели подаётся сфокусированный фрагмент (конкретная статья «до» и «после»), а не весь документ. Между «извлекли текст» и «считаем дельту» обязателен узел вырезания релевантного фрагмента.



8. ИИ-генерация: маршрутизация Qwen / Gateway

8.1. Критерий маршрутизации

Qwen берёт задачи, где он обрабатывает ПРЕДЪЯВЛЕННЫЙ текст. Gateway берёт задачи, где нужно генерировать знание или публичное лицо продукта. Дешевизна — следствие, не цель.

Жёсткое правило (страховка от галлюцинаций): Qwen НИКОГДА не выступает источником юридического знания — только обработчиком предъявленного текста. Локальная модель надёжна как обработчик и опасна как «эксперт по праву».

8.2. Инфраструктура исполнения

Локальная модель (Qwen3 8B) — на домашнем стационаре-сервере. Роль: тяжёлая фоновая/массовая обработка и дефолтные механические задачи. Это НЕ критичный продакшен-узел.

Gateway (облако) — финальный публичный текст и всё, где цена ошибки в репутации высока.

Развязка во времени: Kafka с самого начала (решение принято). Очередь сообщений НЕ размещать на самом домашнем сервере, иначе она умрёт вместе с ним.

Сырьё и база — в резервируемом хранилище (НЕ только на домашнем диске). Домашний GPU читает оттуда и пишет туда результат.

Почему так: домашний сервер = бытовое питание/интернет, без резервирования. Допустимо для фоновой обработки (упало — подождёт), недопустимо как лицо продукта. Очередь обеспечивает буфер при пиках и при простое сервера.

8.3. Самонаполняющаяся база через дельту

Механизм обработки поправки:

Изменяемый акт ЕСТЬ в базе → «было» из базы + «стало» из поправки = полная дельта.

Изменяемого акта НЕТ → (на втором этапе) парсер подтягивает его, кладёт в базу навсегда, дельта становится полной.

Эффект: каждая поправка затягивает в базу ещё один действующий акт. База наполняется по факту реальной потребности — самые часто изменяемые (= самые важные) акты попадают первыми. Это принцип достаточности, а не слепой бэкофилл.

Очерёдность (принятое решение): сначала делаем дельту по тому, до чего дотянулись (где закон сам приводит новую редакцию — показываем полноценно; где только адресная правка — показываем сам патч). Парсер изменяемых актов — ВТОРЫМ этапом.

Статус полноты дельты на карточке (полная / частичная).

Очередь недостающих актов: каждая ссылка на отсутствующий акт записывается («нужен акт X, сослалась поправка Y») — список задач для будущего парсера и статистика спроса.

8.4. Обязательная проверка модели на реальных текстах

До ввода в работу прогнать ≥10 реальных ФЗ-поправок через Qwen и проверить точность привязки «что к чему относится» на юридическом канцелярите. Если точность недостаточна — запасной вариант: локальные модели, дотренированные на русском, на том же железе.



9. Контроль качества: два гейта

Это ДВА разных гейта в двух точках конвейера, ловящие разные породы ошибок разными методами. Объединять их в один нельзя. Гейты нужны для ЛЮБОЙ модели, а не как компенсация Qwen: сильная модель снижает частоту срабатывания, но не отменяет необходимость. Поскольку публикация полностью автоматическая (решение принято), пороги автопроверок выставляются ЖЁСТКО: при сомнении предпочтительнее ложно отклонить (false reject), чем пропустить ошибку в публикацию.

9.1. Гейт №1 — проверка дельты (после узлов 2–3, механический)

Эталон — текст первоисточника. Большая часть проверки выполняется КОДОМ, без ИИ.

Привязка к реальным объектам: упомянутая статья реально присутствует в тексте поправки; номер ФЗ совпадает с заголовком.

Цитатная верность: фрагмент «стало: …» присутствует в тексте поправки ДОСЛОВНО (не по смыслу). Не нашлось дословно → флаг → ручная проверка.

Полнота охвата: число пунктов изменений в источнике совпадает с числом изменений в дельте.

Второй взгляд другой моделью (на семантику адресных правок): проверяет не Qwen, а отдельный вызов (более сильная модель на сомнительных случаях, либо иная постановка вопроса «подтверди/опровергни по источнику»).

Правило: дельта проходит автоматически только при чистых механических проверках. Любой флаг → ручная проверка, не публикация. Для частичной дельты полнота проверяется мягче, цитатная верность «стало» — так же строго.

9.2. Гейт №2 — проверка сводки (после узла 4, заземление на источник)

Принцип grounding: финальная сводка не содержит ни одного факта, которого нет в проверенной дельте и реквизитах. Сводка только переформулирует проверенное.

Конструктивная защита: Gateway получает на вход проверенную дельту + реквизиты и инструкцию использовать только предъявленное, ничего не добавлять (никаких «экспертов» и оценок не из источника). Постановка «переформулируй вот это», а не «напиши о законе».

Проверка соответствия (вторым вызовом): каждое утверждение сводки подтверждается источником; нет ли добавленных фактов.

Числа и даты — отдельным механическим проходом: всякое число/дата в сводке дословно встречается в реквизитах/дельте (защита от выдуманной даты вступления).

Публикация полностью автоматическая (решение принято): чистая карточка публикуется без участия человека. Любая зафлаженная карточка НЕ публикуется автоматически — отводится в очередь ручного разбора. Человек работает только с флагами, не со всем потоком.

9.3. Размещение гейтов и обратная связь

Гейты работают в ФОНОВОМ конвейере, не на пути публикации в реальном времени. Прошедшее оба гейта ложится в «банк готовых карточек». Публикация берёт уже проверенное — ритм не страдает.

Каждый флаг и каждая правка человека сохраняются как сигнал об ошибках модели — материал для улучшения промптов и последующего дообучения.



10. План внедрения Шага 1 по итерациям

Шаг 1 выкатывается не целиком, а шестью маленькими релизами. Нарезка — ПО ЦЕННОСТИ для пользователя, а не по техническим узлам: каждый релиз можно показать и опубликовать.

Принцип нарезки: каждая итерация добавляет РОВНО ОДИН новый тяжёлый элемент. Если в итерацию попадает два тяжёлых элемента — её делят. Поэтому исходные «шаг 1» и «дельта» разбиты на 1a/1b и 3a/3b.



Ключевые точки плана:

После 1a продукт уже в продакшене и проверяет главную гипотезу: читают ли это вообще. Если не читают список со ссылками — саммари не спасёт.

После 1b — полноценный бесплатный продукт «новости с кратким содержанием».

Итерация 2 больше строит актив (самонаполнение базы), чем радует пользователя — её ценность скромная и это нормально.

3a даёт ~80% ценности дельты за ~20% усилий (только «изложить в редакции»). 3b — длинный хвост сложности; выносится отдельно, чтобы не застрять до выхода в продакшен.

После 3a достигнута основная цель Шага 1 — пользователь видит, что конкретно изменилось. 4 — монетизация уже накопленного.

Сквозное и не откладываемое: события версионирования (раздел 6) пишем детально начиная с 1b — когда впервые появляется содержание. Не ради поста, а потому что потерянную гранулярность не добрать. Это единственное оправданное «на вырост».



11. Критерии готовности Шага 1

Шаг 1 считается выполненным, когда одновременно:

Ежедневный сбор: новые ФЗ ежедневно поступают из API, дедуплицируются по eoNumber, сохраняются с полным сырьём (раздел 4.1) и реквизитами (4.2).

Извлечение текста из PDF работает, включая фоллбэк для сканов.

Дельта формируется по доступному уровню (полная / частичная) с проставленным статусом полноты; ведётся очередь недостающих актов.

ИИ-конвейер маршрутизирует задачи по критерию 8.1; узлы 2–3 работают на фрагментах.

Оба гейта качества функционируют; в публикацию попадает только прошедшее проверку.

Еженедельный контент стабильно формируется из «банка готовых» (буфер + отбор + резерв), включая запасные форматы на случай засухи.

Наблюдаемость: метрики сбора (получено/новых/ошибок) и алерт на тихий сбой сбора.

Сырьё и база — в резервируемом хранилище; домашний сервер не является единственным местом хранения.

Структура хранения реализована по разделу 5: сырьё (Кат. 1) в объектном хранилище, структурированные таблицы в реляционной БД, очередь недостающих актов и банк готовых карточек заведены.

Изменения изменяемых норм пишутся как события (norm_change_event) с точкой отсчёта (baseline), структурированным адресом, типом операции и составным порядком — по требованиям раздела 6.4.

Сборка редакции изолирована за единым интерфейсом; на Шаге 1 собирается тривиальный случай full_redaction, address_patch помечается needs_manual и копится.



12. Дорожная карта (Шаги 2–7, без детализации)

Каркас дальнейших шагов для полноты картины. Детализация — по мере подхода к каждому шагу. Каждый шаг проверяется сквозным критерием из раздела 1.3.



Перспектива (смыкается со Шагом 0): по мере накопления базы даже публичную сводку (узел 4) можно частично вернуть на локальную модель, подавая ей проверенный контекст из своей базы — тогда модель снова становится обработчиком предъявленного текста. Это снижает зависимость и от облачных LLM.
