# Ручной OCR-бенчмарк (Приоритет 1.1)

Разовый исследовательский инструмент, не часть продового пайплайна. Закрывает §1.1
`explainlaw_fix_report_v1.md`: собрать вручную выверенную эталонную выборку из 20–30 ФЗ и
прогнать через неё несколько OCR-движков + вариант «OCR + LLM-постобработка», чтобы
подтвердить или опровергнуть текущий выбор `settings.ocr_engine`.

Три метрики считаются и репортятся **раздельно**, не объединяются в одно число:

1. CER/WER по всему тексту (порог ≥98% точности).
2. Точность «критичных элементов» — чисел/дат/сумм/сроков/номеров статей-пунктов (порог
   100%, отдельно от CER/WER: небольшая общая ошибка может испортить юридически значимое
   число, оставаясь незаметной в среднем проценте).
3. Доля служебного мусора/подписей в выводе (цель → 0, это proxy для визуальной оценки, не
   строгий gate).

## ⚠️ Ограничение эталона — прочитать перед вычиткой

У pravo.gov.ru нет независимого текстового слоя ни в `page_snapshot` (только навигационная
обвязка страницы), ни в резервных `zip`-архивах (сканы TIFF без текста) — проверено на
реальном документе. Поэтому черновик эталона генерируется **тем же самым** движком
(по умолчанию Tesseract), который затем участвует в сравнении.

**Риск:** если движок систематически ошибается в одном месте (например, путает `0`/`О` в
номере статьи), а вычитывающий человек не заметит ту же ошибку при чтении черновика — неверный
вариант попадёт в эталон как «верный», и движок получит завышенную оценку именно на этом
фрагменте. Смягчение — обязательные правила вычитки:

- Открывайте `<eo>.draft.txt` **рядом с самим PDF-сканом**, не доверяйте только черновику.
- Читаемость текста — это только первый проход. **Отдельно и внимательно** сверьте с PDF
  каждое число, дату, номер статьи/пункта/части, денежную сумму — посимвольно, не по смыслу.
- Черновик (`<draft-engine>.cleaned.txt`) уже прошёл `strip_signature_block` — блок подписи
  (место/дата/должность/ФИО подписанта) в нём отсутствует. **Верните его в `.reviewed.txt`
  вручную**, сверившись с PDF: §4.1 (CER/WER) сравнивает текст с сохранённой подписью на обеих
  сторонах — без этого шага итоговый CER/WER будет завышен по причине, не связанной с
  качеством распознавания.
- Если `compute_metrics.py` покажет, что черновой движок получил подозрительно идеальный
  `critical_accuracy=100%` при том, что другие движки на том же документе заметно ниже — это
  сигнал перепроверить вычитку вручную, а не факт качества движка.

**Кто вычитывал этот конкретный прогон.** Вычитку всех 15 `.reviewed.txt` в этом репозитории
выполнил Claude (агент), а не независимый человек-разметчик — это дополнительный источник
смещения поверх риска выше: та же модель, что вычитывает эталон, статистически предрасположена
к тем же классам ошибок распознавания образов (спутанные похожие символы, пропущенные
надстрочные знаки), что и OCR-движки, которые эталон затем оценивает. Каждая правка при этом
подтверждалась постранично против самого PDF-скана (не по памяти/языковой модели домена), но
это не заменяет независимую человеческую вычитку — при переносе этого бенчмарка в продовое
решение стоит как минимум выборочно перепроверить `.reviewed.txt` человеком.

**Известный дефект скана — документ `0001202003010004` (47-ФЗ, 2020).** Между страницами 21 и
22 исходного PDF есть содержательный разрыв самого скана (не проблема OCR/вычитки) — черновик
Tesseract демонстрирует ту же разрывность на границе, и `.reviewed.txt` сохраняет её как есть,
не восстанавливая недостающий текст по догадке. Это специфичный для данного документа дефект
исходных данных, а не общая характеристика выборки.

## Порядок запуска

Активируйте `.venv` и убедитесь, что зависимости бенчмарка установлены:

```bash
pip install -e ".[benchmark]"
```

### 1. Пул кандидатов

```bash
cd scripts/ocr_benchmark
python select_sample.py
```

Пишет `data/candidate_pool.csv` (~50–60 строк, сбалансированы по эре публикации × длине
документа). Колонки `has_tables`/`scan_quality`/`include`/`notes` — пустые.

**Ручной шаг:** откройте PDF каждого кандидата (`storage_path` в S3-бакете, либо
`pravo.document_url(eo_number)`), заполните `has_tables` (`yes`/`no`), `scan_quality`
(`clean`/`artifacts`), `include` (`true` для отобранных), `notes`. Сократите до 20–30 строк,
покрывающих все оси (старые/новые, короткие/длинные, с таблицами/без, чистые/с артефактами)
хотя бы по разу. Сохраните результат как `sample_manifest.csv` в этой же папке — именно этот
файл, а не `candidate_pool.csv`, дальше является источником правды.

### 2. Прогон OCR-движков

```bash
python run_ocr.py
```

По умолчанию гоняет `tesseract` и `pymupdf` (PyMuPDF-native OCR) по каждому документу с
`include=true`, **все страницы без обрезки**. Пишет в `data/ocr/<eo>/`:

- `<engine>.raw.txt` — необработанный вывод, склеенный по страницам.
- `<engine>.cleaned.txt` — `strip_signature_block(reflow_soft_linebreaks(raw))`, эквивалент
  продовой нормализации текста.

Повторный запуск пропускает уже посчитанные (движок, документ) пары; `--force` — перегнать
заново; `--eo <eo_number>` (можно несколько раз) — ограничить конкретными документами;
`--engines tesseract,pymupdf,paddle` — включить Paddle явно.

**Paddle исключён из дефолта.** Установленный в этом окружении `paddleocr` (3.x) несовместим
с продовым `PaddleEngine` (написан под 2.x API — другие сигнатуры `.ocr()`/`.predict()`,
другие параметры конструктора), а `paddlepaddle<3.0` не имеет колеса под macOS arm64.
Paddle в проде и так неактивен (`OCR_ENGINE` не задан, дефолт tesseract) — не авария, но
сравнение движков без отдельной задачи по переписыванию `PaddleEngine` под v3 ограничено
Tesseract vs PyMuPDF-native (+ Tesseract+LLM).

Для длинных документов (60–300 стр.) прогон может занять существенное время — прогресс
логируется по страницам каждые 10 страниц.

### 3. LLM-постобработка (псевдо-движок `tesseract+llm`)

```bash
python llm_postprocess.py
```

Постранично прогоняет Tesseract, затем чистит явные артефакты распознавания через LLM
(`create_gateway_client()` с фолбэком на `create_qwen_client()`, temperature=0.1). Промпт
явно перечисляет «защищённые фрагменты» страницы (числа/даты/номера статей-пунктов-частей/
суммы, извлечённые `critical_elements.py` из исходного OCR-текста) и требует сохранить их
байт-в-байт — это первый, «мягкий» слой защиты, и он не идеален (ниже показано, что модель
всё ещё иногда его нарушает).

**Второй, «жёсткий» слой — детерминированный откат.** После ответа LLM критичные элементы
страницы сравниваются до/после; если хоть один пропал или исказился, правка этой страницы
целиком откатывается к исходному OCR-варианту ДО записи в `tesseract+llm.raw.txt` — не просто
помечается флагом. `data/ocr/<eo>/tesseract+llm.altered_critical.flag` фиксирует, что модель
хотя бы раз попыталась нарушить запрет (диагностика, не риск), `tesseract+llm.reverted_pages.txt`
— сколько именно страниц откачено.

**Найден и исправлен инфраструктурный дефект, из-за которого предыдущий прогон этого раздела
был полностью недостоверен.** `explainlaw.config.Settings` резолвит `.env` относительно текущей
рабочей директории процесса (`SettingsConfigDict(env_file=".env")`), а не относительно
расположения `config.py`. Скрипты этого бенчмарка запускаются через `cd scripts/ocr_benchmark
&& python ...` (см. выше) — без явной загрузки `.env` по абсолютному пути настройки LLM тихо
получали пустые/дефолтные значения, `create_gateway_client()`/`create_qwen_client()` оказывались
недоступны, и весь прогон `tesseract+llm` фактически проходил без единого реального вызова LLM
(163 страницы за ~2 минуты — физически невозможно для настоящих сетевых вызовов). Итог
`{'intercepted_docs': 0, 'reverted_pages': 0}` того прогона был ложным и не отражал ни промпт,
ни безопасный откат. Исправлено — `common.py` теперь явно грузит `<repo-root>/.env` через
`python-dotenv` при импорте, независимо от рабочей директории запуска.

Отдельно при повторном (уже настоящем) прогоне обнаружена и устранена утечка служебного токена
`/no_think` (маркер Qwen3 chat-template для отключения reasoning) в хвост ответа модели на одной
из страниц — не критичный элемент, поэтому «жёсткий» слой его не ловит, а WER он бы исказил как
лишний непарный токен. `_strip_control_tokens()` вырезает такие маркеры из ответа модели до
любых дальнейших проверок. Также добавлены ретраи с бэкоффом на пустой ответ клиента (у
используемого здесь Kafka-транспорта под нагрузкой встречается `status="ok"` с пустым текстом
вместо ошибки) и троттлинг между страницами — оба защищают именно от «тихого» повторения
описанного выше сбоя, а не от нового наблюдавшегося случая (в этом прогоне пустых ответов не
было ни разу).

**Реальные цифры этого (исправленного) прогона.** Из 15 документов в 5 модель хотя бы раз
попыталась нарушить запрет промпта на критичный элемент (8 страниц суммарно из 163) — во всех
5 случаях откат сработал, ни один искажённый критичный элемент не попал в
`tesseract+llm.raw.txt`. Для сравнения, в первом (пред-безопасном) прогоне до внедрения жёсткого
отката искажение доходило до финального текста в 9 из 15 документов (60%). Защищённые фрагменты
в промпте снизили частоту самих попыток нарушения примерно вдвое (9→5 документов), а жёсткий
откат обнулил долю искажений, реально попадающих в финальный вывод, до 0 из 15 — по построению,
а не только эмпирически по итогам конкретного прогона.

**Новый, более серьёзный найденный риск: модель придумывает целые абзацы юридического текста,
когда OCR полностью проваливается на фрагменте страницы, а не только путает похожие символы.**
На документе `0001201602150045` (269-я статья НК, п. 2-4) исходный Tesseract-текст на этом
месте — нечитаемый мусор («„А. ВИ»), т.к. скан в этом месте плохого качества. Вместо того чтобы
оставить мусор как есть, модель написала три связных, грамматически правильных абзаца
юридического текста — но содержательно НЕВЕРНЫХ: сверка с `.reviewed.txt` (вычитанным против
PDF эталоном) показывает, что придуманный текст не совпадает по смыслу с реальными пунктами 2-4
статьи 269 (реальные — про перечень контролируемых долговых обязательств перед иностранным
взаимозависимым лицом и коэффициент капитализации; придуманные — общая фраза про «производство
и реализацию товаров», не имеющая отношения к содержанию). Это НЕ ловится безопасным откатом
критичных элементов: в мусорном исходном тексте не было ни одного распознаваемого числа/даты/
ссылки на статью, которые можно было бы сравнить до/после — сравнивать физически не с чем, а
результат при этом выглядит убедительно и уверенно. Именно этот случай — главная причина, почему
медианный CER `tesseract+llm` в сводке ниже стал ХУЖЕ, чем у чистого Tesseract (0.0342 против
0.0155), несмотря на то что в среднем по документу модель чинит реальные артефакты OCR (спутанные
символы, лишние обрывки) корректно и по мелочи улучшает WER.

**Вывод.** Безопасный откат защищает от одного класса риска (искажение уже распознанного числа/
даты/ссылки на статью) и делает его нулевым по построению. Он не защищает от другого, более
опасного класса — уверенной выдумки целых юридических абзацев взамен нечитаемого OCR-мусора,
которая ничего не нарушает в списке защищённых фрагментов просто потому, что там нечего было
защищать. `tesseract+llm` в текущем виде не готов к продовому включению; дальнейшее смягчение
потребует отдельного шага — детектировать страницы/блоки с аномально низким качеством OCR
(короткий/мусорный текст относительно ожидаемого объёма) и на них LLM-постобработку не запускать
вовсе, оставляя видимый OCR-мусор вместо невидимой подмены.

### 4. Черновик эталона + статус вычитки

```bash
python fetch_ground_truth.py            # сгенерировать недостающие черновики
python fetch_ground_truth.py --status   # только показать, что ещё не вычитано
```

Берёт `data/ocr/<eo>/<draft-engine>.cleaned.txt` (по умолчанию `tesseract`, флаг
`--draft-engine`) и копирует как есть в `data/ground_truth/<eo>.draft.txt`. Если исходного
файла ещё нет — явная ошибка с подсказкой сначала прогнать `run_ocr.py` для этого документа
(не тихий пропуск).

**Ручной шаг:** см. предупреждение выше. Результат вычитки сохраните как
`data/ground_truth/<eo>.reviewed.txt` — **полный текст документа, включая блок подписи**.
`compute_metrics.py` использует только `.reviewed.txt`; `.draft.txt` эталоном никогда не
считается.

### 5. Метрики и отчёт

```bash
python compute_metrics.py
```

Для каждого документа с готовым `.reviewed.txt` и для каждого движка, у которого есть
`<engine>.raw.txt` в `data/ocr/<eo>/`, считает CER/WER (обе версии текста — с сохранённой
подписью, через `reflow_soft_linebreaks`+`normalize_whitespace`; `_raw` — без
`fix_ocr_artifacts`, `_fixed` — с ним), точность критичных элементов и мусорные
proxy-метрики. Пишет:

- `raw_metrics.csv` — построчно (документ, движок).
- `report.md` — сводная таблица по движкам с PASS/FAIL по порогам §1.1, худшие документы на
  движок, раздел `tesseract` vs `tesseract+llm`, раздел с оговорками.

Документы без `.reviewed.txt` пропускаются с явным warning в логе и отдельным списком в
`report.md` — не участвуют в сводке молча.

## Структура каталога

```
scripts/ocr_benchmark/
  common.py               # пути, датаклассы, бакеты, CSV-хелперы
  select_sample.py        # этап 1 — пул кандидатов
  run_ocr.py               # этап 2 — прогон движков (tesseract, pymupdf, [paddle])
  llm_postprocess.py       # псевдо-движок tesseract+llm (импортирует safety-net из прода)
  fetch_ground_truth.py    # этап 3 — черновик эталона + статус вычитки
  metrics.py               # CER/WER (jiwer) + мусор/подписи
  compute_metrics.py       # этап 4 — raw_metrics.csv + report.md
  sample_manifest.csv      # трекается — итоговая размеченная выборка (20-30 строк)
  report.md                # трекается — финальный отчёт
  raw_metrics.csv          # трекается — сырые метрики по (документ, движок)
  data/                     # gitignored — PDF-кэш, черновики/вычитанные эталоны, дампы OCR
```

`critical_elements.py` и двухслойная LLM-очистка (промпт с защищёнными фрагментами + жёсткий
откат при расхождении критичных элементов) переехали в прод — см. раздел ниже.

## Промоушен в прод: retry-и-drop для нечитаемого OCR

По итогам этого бенчмарка (в частности, случая `0001201602150045`, см. предупреждение в начале
файла) в прод добавлена защита от нечитаемого OCR (`src/explainlaw/pipeline/processor.py`,
`_process_document`): при обнаружении мусора (`extraction/quality.py::is_text_unreadable`) —
передокачка PDF с портала → повторный OCR →, если текст стал читаемым, косметическая
LLM-очистка (`extraction/llm_cleanup.py`, перенос двухслойной защиты отсюда) → если текст
всё ещё мусор даже после передокачки, документ помечается `NpaText.is_unreadable=True` и
навсегда исключается из выборки на обработку и из сводки, LLM на нём не вызывается вообще.

**Осознанное ограничение (по прямому решению пользователя):** gate работает на уровне всего
документа целиком, не постранично. Он поймает документ, который в среднем нечитаем, но **не
поймает** ровно случай `0001201602150045` — документ, который в среднем читается нормально (11
страниц), а проблема в одном сфабрикованном LLM абзаце внутри. Приоритет отдан простоте
документо-уровневого гейта по прямому запросу пользователя, а не постраничной детекции.
